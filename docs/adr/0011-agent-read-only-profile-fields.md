# プロフィールにはエージェントだけが読む項目を置き、読む手順とセットで足す

- ステータス: 承認済み
- 日付: 2026-07-25

`config/profile.json` の項目は「CLIのコードが読むもの」（`height_cm`・`day_start_time` 等）と
「エージェントだけが読むもの」（`routine`・`allergies`・`dietary_restrictions`・
`advice_preference`）に分かれる。後者を足すときは、器（JSON Schema）だけでなく
**読む手順をスキルとAGENTS.mdに同時に置く**。手順の無い器は設定しても何も起きず、
利用者からは動かない機能と見分けがつかないため。

## コンテキスト

`advice_preference`・`dietary_restrictions`・`allergies` はv1からスキーマにあり、
READMEにも「助言の文脈」と書かれていたが、どのスキルにも読む手順が無く、値を入れても
出力は変わらなかった。ADR 0004 はこれを「スキーマに項目だけ定義しコードから読まない前例」
として引き合いに出していたが、`routine` との本当の違いは *コードが読まないこと* ではなく
*手順がどこにも無いこと* だった。同時に `plans.protein_target` も同種の空の器として
残っていたため、こちらは列ごと削除した（マイグレーション7）。

## 検討した代替案

- **3項目をスキーマから削除する** — 器を消せば不整合は消えるが、`advice_preference` には
  実際に値が入っており、利用者が助言に反映されることを期待して書いたものだった。
  期待自体は妥当なので、器ではなく手順のほうを足す。
- **CLIのコードから読ませる** — アレルゲンの照合も助言の書き方も、断定を避ける言い回しや
  「本人が承知のうえかどうか」といった会話の文脈に依存する判断で、ADR 0004 と同じ理由で
  コードに置くと硬直する。

## 結果

- エージェントが `advice_preference` を反映するのは**自分の言葉で書く文章だけ**。
  `diet report` と `diet advice` がCLIで生成した文言は、数値も助言文も正本なので
  この方針で書き換えない。
- アレルギー・食事制限に該当しそうな品目があっても記録は止めず、そのまま登録したうえで
  「〜の可能性がある」と一言添える。写真やメニュー名から原材料は断定できず、
  症状や対処の判断は医療行為にあたるため踏み込まない。
- 手順の置き場所は `routine` と同じく、record-meal / write-report スキルと
  AGENTS.md の「定型作業」節。
