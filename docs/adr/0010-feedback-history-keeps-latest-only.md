# フィードバックは種別・期間ごとに最新1件だけを保持する

- ステータス: 承認済み
- 日付: 2026-07-25

> このADR内の識別子は決定当時の名称。現在の`feedback`名への変更はADR 0015を参照。

フィードバックは`diet report`や`diet advice`を実行するたびに生成されるため、追記型では読み取り操作の
たびに`advice_history`が増え続けていた（食事26件・6日分の記録に対し110行、同じ日の日次フィードバックが
最大23行）。そこで`(advice_type, period_start, period_end, COALESCE(meal_id, 0))`を一意キーとし、
同じキーのフィードバックは上書きする。行数は「記録した日数 + 食事件数」に収まり、何度実行しても増えない。
食後フィードバックは`details`のJSON内にあった`meal_id`を列へ出してキーにした。

## 検討した代替案

- **旧行を`status='superseded'`にして追記する**: 監査証跡は残るが、行が増え続ける問題そのものは
  解決しない。[0009](0009-goal-deletion-is-logical.md)で目標を論理削除にしたのは、過去のレポートが
  根拠にした摂取目標を復元するためだった。フィードバックは同じ根拠（記録と計画）から再生成でき、
  レポートも保存済みのフィードバックを読まないので、途中経過を残す必要がない。
- **内容が完全一致する場合だけ挿入を抑制する**: 日次フィードバックは食事を記録するたびに文面が変わるため
  110行が54行になる程度で、上限が付かない。
- **読み取り系コマンドで`save=False`にする**: フィードバックをユーザーへ提示する経路がレポートそのもので、
  保存されるのは食事記録時だけになる。「最後にどんなフィードバックを返したか」が残らない。

## 結果

`status`列は常に`'active'`で使われていなかったため削除した。マイグレーション6は既存の重複行を
キーごとに最新1件へ圧縮し、対象の食事が既に削除されている食後フィードバックは捨てる。
`initialize()`は`SCHEMA_SQL`より先にマイグレーションを適用する順序へ変えた
（`SCHEMA_SQL`は最新スキーマ前提の索引を含むため、列の追加より先に流すと失敗する）。
