# LLM APIを用いたアプリ化の検討

- 検討時点: 2026-07-27
- ステータス: 比較検討中。モデル、API事業者、構成はいずれも未決定

## 結論

Diet Assistantをアプリとして提供する場合、現在エージェントが実行しているSkillは、
LLM API固有の「Skill機能」に依存せず、アプリケーションのワークフローとして実装できる。
LLMには食事の画像・文章の解釈、構造化データの生成、ツール選択、フィードバックの執筆を
担当させ、保存、集計、判定、検証は既存のサービス層とSQLiteに担当させる。

この分離を行えば、最上位の推論モデルを常用する必要はない。通常処理には、
画像入力、構造化出力、Function Calling、日本語生成を安定して扱える中価格帯の
マルチモーダルモデルを使い、難しい入力だけ高性能モデルへフォールバックする構成が有力である。

2026年7月時点の中国系モデルでは、単一モデル構成の第一候補は`qwen3.7-plus`、
品質上限は`kimi-k3`、対抗候補は`glm-5v-turbo`である。`deepseek-v4-flash`と
`MiniMax-M2.7`は安価だがテキスト専用なので、写真解析後のフィードバック生成などに用途を限定する。

## 検討の前提

- オープンウェイトモデルもセルフホストせず、公式または第三者の推論APIで利用する。
- OpenAIだけに限定せず、Google、Anthropic、Mistral、中国系各社、ホストされた
  オープンウェイトモデルを比較する。
- 同じウェイトでも、量子化、チャットテンプレート、画像処理、Tool Calling実装が
  API事業者ごとに異なる。そのため、評価単位はモデル名だけでなく
  **モデルとAPI事業者の組み合わせ**とする。
- 個人の食事写真、プロフィール、身体測定値を扱うため、価格と性能だけでなく、
  データ保存期間、学習利用の有無、処理地域、削除手段、契約条件も選定条件にする。
- モデルと価格は変化が速いため、ここに記載する一覧は2026年7月27日時点のスナップショットとする。

## 現在のSkillをAPIから使えるか

### 結論

同等の機能は実現できる。ただし、リポジトリ内の`SKILL.md`をそのまま実行できるかどうかを
プロバイダー選定条件にはしない。

現在のSkillは、次の3要素に分解できる。

1. 実施順序、確認条件、禁止事項などの手順
2. `diet`コマンドが提供する保存、取得、集計、検証機能
3. 画像や文章を解釈し、フィードバックを書くLLMの判断

アプリ化後は、1をアプリケーションの状態遷移とバリデーション、2を既存のサービス層または
APIツール、3をLLM呼び出しとして実装する。プロバイダー固有のAgent SkillやMCP対応は
開発効率を上げる可能性があるが、製品の中核にはしない。

### 食事記録の対応

`record-meal` Skillが担う処理は、次のワークフローに置き換えられる。

```text
写真・文章
    │
    ▼
LLMによる品目・量・栄養値レンジ・確信度の推定
    │
    ▼
JSON Schema検証
    │
    ▼
アレルギー・食事制限・ルーティーンの機械的確認
    │
    ▼
application serviceによるSQLiteへの保存
    │
    ▼
保存結果の再取得・検証
    │
    ▼
LLMによる短いフィードバック
```

LLMの出力を直接DBへ書かず、必ずスキーマ検証とサービス層を通す。写真だけから食品や量を
断定せず、最小値、最大値、代表値、確信度、推定根拠を構造化して保持する。

### レポート作成の対応

`write-report` Skillでは、既存の責務分離を維持する。

- CLIまたはサービス層が、SQLiteを正本として分析結果（findings）を生成する。
- LLMはfindingsに含まれる事実と数値だけを根拠にフィードバックを書く。
- アプリケーションがフィードバックを保存し、レポートへ埋め込む。

この構成は[ADR 0013](adr/0013-agent-writes-feedback-cli-owns-findings.md)と一致する。
栄養計算や傾向判定をLLMへ移す必要はない。

## LLMに求める能力

一般的なチャット性能より、次の能力を優先する。

1. 食事写真から複数品目を見落とさず抽出できる
2. 分量を一点で断定せず、妥当なレンジと確信度を返せる
3. JSON SchemaまたはJSON Modeへ高い確率で従える
4. Function Callingで許可されたツールと引数を正しく選べる
5. findingsに存在しない数値、頻度、食品をフィードバックへ追加しない
6. 日本語で短く、行動可能で、過度な食事制限を勧めない文章を書ける
7. 不鮮明な写真や不確実な入力では、断定せず確認またはフォールバックを選べる

保存、集計、栄養目標の計算、レポート日の決定、トランザクションはアプリケーション側に残す。
このため、長時間の自律コーディングや巨大コンテキスト処理は通常の食事記録には必須ではない。

## 2026年7月時点の中国系モデル

### 最新世代

| 会社 | 現行世代 | 入力 | このアプリでの位置付け |
|---|---|---|---|
| Moonshot AI | Kimi K3 | テキスト、画像 | 品質上限、難しい入力へのフォールバック |
| Alibaba | Qwen3.7 Max | 主系列はテキスト | 高性能な文章・推論処理 |
| Alibaba | Qwen3.7 Plus | テキスト、画像、動画 | 単一モデル構成の第一候補 |
| DeepSeek | DeepSeek V4 Pro / Flash | テキスト | 安価なフィードバック生成、画像処理後の推論 |
| Z.ai | GLM-5.2 | テキスト | 高性能な文章・推論処理 |
| Z.ai | GLM-5V-Turbo | テキスト、画像、動画、ファイル | Qwen、Kimiに対するマルチモーダル対抗候補 |
| MiniMax | MiniMax M2.7 | テキスト | 安価な文章生成、Agent処理 |

Kimi K3は2026年7月16日に発表された2.8Tパラメータのオープンモデルで、
ネイティブVisionと1Mトークンのコンテキストを持つ。常にthinkingを行い、
`reasoning_effort`で`low`、`high`、`max`を選択する。通常の食事登録には
過剰な可能性があるため、常用モデルではなく品質上限として評価する。

Qwen3.7 MaxはQwenの最上位系列だが、画像を含むアプリの標準モデルとしては
Qwen3.7 Plusの方が扱いやすい。Qwen3.7 Plusは画像・動画入力、Function Calling、
Structured Output、1Mトークンのコンテキストをサポートする。

DeepSeek V4とMiniMax M2.7は現行の高性能・低価格モデルだが、テキストAPIは画像入力を
受け付けない。食事写真を扱うには別のVisionモデルが必要である。

### オープンウェイトとAPI専用モデルを分ける

中国系モデルであることと、オープンウェイトであることは同じではない。
例えばKimi K3とDeepSeek V4はオープンウェイトかつ公式APIを持つ一方、
Qwen3.7 Max / PlusはAlibabaのAPIモデル系列である。Qwenのオープンウェイト系列を
評価する場合は、Qwen3.7 API系列とは別枠で、利用するウェイトと推論事業者を固定して比較する。

オープンウェイトAPIでは、次の情報を記録する。

- ウェイトの正確な名称とリビジョン
- 推論API事業者
- 量子化方式
- thinkingの有無と設定
- コンテキスト長と最大出力
- Vision、JSON Schema、Function Callingの対応状況
- リージョン、データ保持、SLA

## コスト試算

### 仮定

1人のアクティブユーザーが1か月に次を利用すると仮定する。

- 食事記録: 90回
- 日次レポート: 30回
- 週次レポート: 4回
- 合計: 約124回
- 課金対象入力: 0.5Mトークン
- 課金対象出力: 0.1Mトークン

月額概算は次の式で求める。

```text
0.5 × 1M入力単価 + 0.1 × 1M出力単価
```

画像トークン、thinkingトークン、ツールの往復、再試行を0.5M入力・0.1M出力の中に
含めた粗い比較である。実際の料金は評価ログから再計算する。

## 有力な構成

### 1. Qwen3.7 Plus単独

Vision、Structured Output、Function Callingを1モデルで扱う。価格と実装の単純さの
バランスがよく、最初に評価する構成とする。

### 2. Kimi K3単独

最新オープンウェイトモデルの品質上限として評価する。通常処理でQwen3.7 Plusとの差が
小さければ常用せず、難しい写真や通常モデルの失敗時だけ呼び出す。

### 3. GLM-5V-Turbo単独

単一モデル構成におけるQwen3.7 Plusの対抗候補。画像理解だけでなく、
ツール呼び出しと日本語フィードバックまで一連で評価する。

### 4. Visionモデルとテキストモデルの分業

Qwen3.7 PlusまたはGLM-5V-Turboで写真を構造化し、DeepSeek V4 Flashまたは
MiniMax M2.7でフィードバックを書く。単価は下げられるが、プロバイダー間のデータ移送、
障害点、評価対象、実装量が増える。単一モデル構成で必要な品質と費用を確認してから検討する。

## 評価方法

公開ベンチマークだけで採用モデルを決めず、このリポジトリ固有の匿名化評価セットを作る。
最初は50〜100件を目安に、簡単な入力、複数品目、不鮮明な写真、パッケージ表示、
テキストのみ、確認が必要な入力を含める。

| 評価項目 | 初期目標 |
|---|---:|
| JSON Schema検証の初回成功率 | 99.5%以上 |
| ツール名・引数の初回成功率 | 99%以上 |
| findingsにない数値を生成しない率 | 99.5%以上 |
| 保存後の検証成功率 | 100% |
| 品目抽出、分量レンジ | 人手で妥当性を判定 |
| 日本語フィードバック | 正確さ、簡潔さ、行動可能性を人手評価 |
| レイテンシ | p50、p95を記録 |
| コスト | 成功した1食事記録、1レポート当たりで記録 |

画像から得られる栄養値には唯一の正解がないため、一点推定の誤差だけで評価しない。
品目の見落とし、分量レンジに妥当な値が含まれるか、確信度が不確実性と対応しているかを重視する。

モデル更新やAPI事業者の変更時は、同じ評価セットを再実行する。`latest`のような
自動更新エイリアスだけに依存せず、本番では可能な限りスナップショットを固定する。

## セキュリティと運用

- 写真、プロフィール、DB全体を必要なく外部へ送らない。
- LLMへ送るのは、その処理に必要な最小限の画像、入力、findingsに限定する。
- APIキーをクライアントアプリへ埋め込まず、サーバー側で保持する。
- リクエスト、レスポンス、使用モデル、モデル版、トークン数、ツール実行結果を
  個人情報を除いて監査可能にする。
- モデルの出力は信頼せず、JSON Schema、値域、権限、状態遷移をアプリ側で検証する。
- DB更新は既存どおりトランザクションを使い、LLMへ直接DB操作権限を与えない。
- 医療的な診断や治療判断をモデルへ委ねない。
- 中国本土、シンガポール、東京など、利用リージョンごとの規約とデータ処理条件を
  リリース前に法務・プライバシー要件と照合する。

## 現時点の推奨

1. Skillをアプリケーションワークフローへ移し、LLM APIを交換可能にする。
2. 最初の評価対象をQwen3.7 Plus、Kimi K3、GLM-5V-Turboの3つにする。
3. 非中国系モデルを少なくとも1つ、品質と運用の対照群として加える。
4. DeepSeek V4 Flashはテキスト処理の低価格候補として、単一モデル評価後に追加する。
5. 最終選定は公開ベンチマークではなく、食事記録とフィードバックの固有評価で行う。

費用だけを見れば複数モデル構成が有利だが、この利用量では単一モデル構成でも
1 MAU当たり月数十セントから数ドルである。初期リリースでは実装と運用の単純さを優先し、
利用量が増えてからルーティングによる最適化を検討する。

## 未決事項

- 写真やプロフィールを処理できるデータリージョンと契約条件
- 目標レイテンシと許容するフォールバック時間
- モデル障害時に別プロバイダーへ切り替えるか、再試行だけにするか
- 利用者へ推定根拠、確信度、利用モデルをどこまで表示するか
- 画像をLLM APIへ送る前に端末またはサーバーで縮小・匿名化するか
- 1ユーザー当たりの月額原価上限
- 第三者推論APIでオープンウェイトを利用する場合のSLAと出力差
